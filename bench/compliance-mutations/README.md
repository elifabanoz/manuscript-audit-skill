# Compliance mutation benchmark

This scorer measures rule-level detection of controlled guideline violations. Manuscripts, guideline caches, agent records, raw candidates, and benchmark case labels stay outside Git. The repository contains benchmark tooling, source identifiers, and invented tests. No empirical M1 result is claimed here.

`public-papers.json` identifies four published JOSS articles ([09737](https://joss.theoj.org/papers/10.21105/joss.09737), [06825](https://joss.theoj.org/papers/10.21105/joss.06825), [09910](https://joss.theoj.org/papers/10.21105/joss.09910), [10374](https://joss.theoj.org/papers/10.21105/joss.10374)) and two JOSE articles ([00059](https://jose.theoj.org/papers/10.21105/jose.00059), [00307](https://jose.theoj.org/papers/10.21105/jose.00307)) by DOI and pins their public Markdown sources with SHA-256 hashes. The article pages state CC BY 4.0 for the published papers. JOSE 00307 and JOSS 10374 are pinned to the release versions named in their [JOSE review](https://github.com/openjournals/jose-reviews/issues/307) and [JOSS review](https://github.com/openjournals/joss-reviews/issues/10374). Retrieve the sources privately with `python bench/compliance-mutations/fetch_public_papers.py /absolute/private/directory`; the downloader verifies each hash and refuses any destination inside a Git checkout. For JOSE 00307 it also retrieves the bibliography and repository license from the same pinned commit into `jose-00307-v1.2.2/`, preserving their submitted basenames. Inspect that license before reusing repository content. No paper, bibliography, or license text is stored in this repository. The additional JOSS and JOSE sources have been downloaded and hash-checked, but they have not yet been human-labeled or scored in a compliance run. The 09910 and 10374 sources each meet the seven verified JOSS heading checks in provisional private checks; this does not establish compliance with semantic rules or other current instructions. JOSS 10374's pinned Markdown date uses ISO format, which differs from the current JOSS date instruction, so it must not be assumed to be a fully compliant control.

The downloader's `output_name` is a local storage name, not the paper's submitted filename. Before testing a filename-sensitive rule, prepare the run from a privately named copy whose name matches the pinned source repository path, and verify that copy's hash against `source_sha256`. Runs prepared before `submitted_filename` was recorded cannot establish filename compliance from their normalized `manuscript.md` path.

To prepare reproducible structural proposals from an already prepared private control run, use `python bench/compliance-mutations/propose_heading_mutations.py /absolute/private/control-run --article-type "Software paper" --output-root /absolute/private/proposals`. The tool checks the control's source-backed deterministic rules, removes exactly one Markdown heading marker per proposed mutation, and records control and mutation hashes. Use repeated `--rule-id` to narrow the selection. It creates no agent findings, labels, scores, or Git-tracked manuscript text. Seven such proposals were prepared privately from JOSS 09910; they remain unreviewed and are not included in the published heading-suite result. A human must verify the baseline and each single-change mutation before any broader benchmark claim.

For a newer control whose two profile drafts have not yet been reconciled, run `python skills/manuscript-audit/tools/check_deterministic.py /absolute/private/control-run --article-type "Software paper" --profile-draft profile-a.json --no-write` to screen the first source-validated draft. This prints a provisional, draft-hashed measurement without writing `deterministic-checks.json`. It cannot qualify a compliant control or replace the independent second draft and human labels.

For a semantic or numerical/format proposal, write a private recipe outside Git with `schema_version`, `article_type`, a verified `rule_id`, `mutation_class` (`semantic` or `numerical_format`), and exact single-line `original` and `replacement` text. Run `python bench/compliance-mutations/propose_text_mutation.py /absolute/private/control-run --recipe /absolute/private/recipe.json --output-root /absolute/private/proposals`. The tool verifies the control run and profile, requires a unique original span, preserves line and heading structure, and records hashes without publishing the edited manuscript. A date-format recipe may replace only the value of the YAML `date` field when it targets `metadata_date_format`. The output is an unreviewed proposal, not evidence that the baseline complies or the edit violates its target rule. Date-format and AI-use-disclosure proposals were prepared privately from JOSS 09737; their baseline and mutation labels still need independent human review.

A [limited heading suite](heading-suite-results.json) records seven verified JOSS heading checks on that published source and seven controlled mutations, each removing one Markdown heading marker while retaining its text and section body. Its recorded raw and independently validated checks each detected 7/7 injected heading violations; neither flagged the one structural control. The recorded validation-stage false-positive-rate reduction was zero. The original private case manifest and agent records are not in the current M1 workspace, so this historical snapshot cannot be replayed here. Sixty-three other applicable rules were excluded, and human control labels remain pending. These counts cover one paper and a single mutation type; they are not M1 recall or false-positive estimates for full manuscript compliance.

Prepare each control and mutated manuscript as a separate private run with the same `--data-freeze YYYY-MM-DD` value. Use the same journal profile and guideline snapshot for each pair. Build a coverage ledger for the selected article type, actually check every rule selected for scoring, and save a current check record for each such unit. Rules marked `needs_validation` remain pending. In schema version 5, a verified rule excluded from scoring may be pending or already covered; its scope record still needs a reason and human approval before final rates. Earlier versions score all verified applicable rules. Save the phase 3 candidates as `raw-findings.json` directly in each run, with entries containing `category: "compliance"` and an applicable `rule_id`. Complete phases 4 and 5 in the run's `findings.json` and independent records. Every confirmed compliance rule must have appeared in the raw candidates. The scorer requires complete coverage of scored rules and runs the full local validator on every run before counting a confirmed finding.

For new quote-audited runs, use case-manifest schema version 4. Each raw candidate must contain exactly `category`, `rule_id`, and a nonempty `evidence` array with at least one guideline quote. Quote entries use either `{"type":"guideline","source_ref":"src_...","quote":"..."}` or `{"type":"manuscript_quote","path":"manuscript.md","line_id":"L12","quote":"..."}`. The scorer checks exact quotes against the pinned private guideline or manuscript bytes and reports unsupported raw quotes divided by all raw quote entries, alongside the number of confirmed quotes surviving validation. A missing or malformed quote rejects the case rather than improving its measured rate. Versions 1–3 remain readable, but they do not produce a raw-quote rate. The rate measures quotation support, not whether the candidate's interpretation is correct; human review is still required for the compliance labels.

Use case-manifest schema version 5 for new benchmark studies that include rules whose source wording is verified but whose compliance cannot be judged from the supplied files. It retains the proposal and quote checks from version 4 and requires a `scope_record` path in every case. Run `python bench/compliance-mutations/prepare_scope_review.py /absolute/private/run --article-type "original_research"` to create an unfilled `scope-review.template.json` inside that private run. Review every rule and save the completed copy as `scope-review.json` directly in the same run. It must name every applicable rule and pin the run manifest, profile, and article type. For each rule, choose `score` or `exclude` and give a concrete reason. A source rule marked `needs_validation` cannot be scored. A verified rule may be excluded when its required evidence is absent or concerns an external or later process; this does not mean the manuscript complies with it. The mutation and paired control must score the same rules. The scorer records each exclusion and the scope-file hash in its private output. It will not score a case with a missing, incomplete, stale, or unreasoned scope record.

For human review before scoring, run the same command with `--review-packet --proposal /absolute/private/run/scope-review.proposed.json` to create a private `scope-review-worksheet.md`. The optional proposal must match the pinned manifest, profile, article type, and every applicable rule. The worksheet shows each rule's short source quote, suggested decision and reason, supplied file hashes, and blank fields for two reviewers and adjudication. It does not approve the proposal or create `scope-review.json`; reviewers must inspect the pinned files and enter their adjudicated decisions in the JSON record themselves. Omit `--proposal` to review every rule without suggestions.

Example private scope record (replace hashes and cover **every** applicable rule):

```json
{
  "schema_version": 1,
  "manifest_sha256": "<sha256 of run-manifest.json>",
  "profile_sha256": "<sha256 of journal-profile.json>",
  "article_type": "original_research",
  "rules": [
    {"rule_id": "data_availability", "decision": "score", "reason": "The supplied manuscript can show the required statement."},
    {"rule_id": "author_consent", "decision": "exclude", "reason": "Author consent cannot be established from the supplied manuscript files."}
  ]
}
```

Version 5 also adds `scope_review_sha256` to each of the two human review records and the adjudication record in `human-labels.json`. Generate the unfilled JSON template with `prepare_label_review.py --format json`, inspect every inclusion and exclusion in the private scope files, then enter the `Scope records SHA-256` value shown in the Markdown worksheet into each approved record. The finalizer rejects missing or stale scope approvals. A matching hash records an approval assertion; it cannot prove a person actually reviewed the scope. Earlier schema versions remain readable for historical cases, but they do not provide this scope gate.

Version 5 also reports raw and independently validated **off-target rule flags** in mutation cases, both per case and as case/rule counts overall and by mutation class. These are scored rules other than the injected target rule. An off-target raw candidate remains visible even when validation leaves it unresolved. Candidates on rules later excluded from scoring remain in the private run and receive quote auditing; the case row lists them separately as `out_of_scope_raw_rule_ids` or `out_of_scope_validated_rule_ids`, without counting them in recall or off-target flags. Target-rule recall does not include off-target flags, and the control false-positive rate does not measure them. They are not automatically false positives: reviewers must decide whether the underlying rule was already violated in the control or whether the mutation affected more than one rule. The current human-label gate labels every scored control rule and each mutation target, but does not adjudicate off-target mutation rules; do not present these counts as an off-target false-positive rate or general precision estimate.

  "data_freeze": "2026-10-19",
  "cases": [
    {

      "run": "/absolute/private/control-run",

    {

Run `python bench/compliance-mutations/score.py /absolute/private/cases.json`. It creates `compliance-mutation-scores.json` beside that manifest and refuses to overwrite it. Paths on Windows must be absolute Windows paths with JSON backslashes escaped. The output contains case IDs, rule IDs, input hashes, recall on injected violations, case-level false-positive rates on controls, and the difference between raw and validated false-positive rates. A mutation is refused when its target rule was already flagged in its paired control; investigate that baseline before scoring. A control with verified deterministic rules needs a matching check report in which those rules are met; triggered or unresolved checks exclude it as a compliant control. The scorer recomputes that report from the hashed private manuscript and sources without changing the run, so edited or stale measurements are rejected. The scorer also rejects changed journal profiles, source snapshots, and freeze dates.

Version 2 requires each mutation to name its class: `structural` for document structure, `semantic` for the meaning or presence of a required statement, or `numerical_format` for limits and prescribed formats. The result reports recall and paired-control false-positive rates separately for each class. A control used by several mutations counts once within each class that uses it; class rates can therefore share a control and must not be treated as independent samples. The scorer accepts existing version 1 manifests without class rates.

For proposal-backed cases, use schema version 3 and add `proposal_record` (an absolute private path to `proposals.json`) and `proposal_file` (the selected mutation filename) to each mutation case. The scorer checks the proposal against the paired control's run, manifest, profile, article type, target rule, and mutation class. It also checks that the proposal manuscript and mutation run have the same hash, and includes the proposal record hash in the scored row. This binds the scored bytes to the prepared proposal; it does not prove baseline compliance, the intended violation, or the absence of collateral changes. Those judgments still require independent human labels. Versions 1 and 2 remain available for earlier results.

The control label needs human review: publication in a journal does not prove the paper complies with every current instruction. A detected mutation does not establish that all other findings are correct. Keep the mutation recipe, license check, source identifiers, and independent adjudication notes with the private case manifest. Publish aggregate results only after those labels and the full case set have been checked; the output hashes allow the result to be tied to its exact private inputs without redistributing manuscripts.

Before agent findings or a scored case manifest exist, run `python bench/compliance-mutations/prepare_preflight_review.py /absolute/private/control-run --article-type "Software paper" --proposal-record /absolute/private/proposals/proposals.json --output /absolute/private/preflight-review.md`. Repeat `--proposal-record` for more proposals tied to the same control, or omit it to review a baseline alone. This creates an unfilled private packet with every applicable profile rule, pinned source and manuscript hashes, the recorded submitted filename, every supplied supporting file's submitted name and hash, and verified proposal file hashes. It distinguishes submitted filenames from normalized private paths and labels missing filename evidence explicitly. It validates the run manifest, supplied file hashes, source-backed profile quotes, and proposal identity without reading agent findings or requiring coverage records. Two human reviewers can label the baseline and each proposed edit independently before agent results are available; they must still inspect the actual manuscript, supporting files, and source pages. The packet does not establish profile-builder independence, control compliance, mutation validity, or benchmark rates.

Run `python bench/compliance-mutations/prepare_label_review.py /absolute/private/cases.json` after the scored runs exist to create an unfilled `human-label-review.md` beside the private manifest. The worksheet lists each scored control rule, each mutation target, short source excerpts, source URLs, submitted filenames for the manuscript and supporting files, private file paths, and SHA-256 hashes. A reviewer checks the manuscripts, supporting files, and source snapshots before reading agent findings, records a decision and evidence location for each rule, and checks whether each mutation changed only the intended property. A second reviewer records disagreements and adjudication. The generator validates the runs and refuses to write inside Git or overwrite an existing worksheet; it does not produce human labels or certify that review occurred.

Run the same command with `--format json` to create a private, unfilled `human-labels.template.json` tied to the exact case-manifest hash and scored-input hashes. Copy it to `human-labels.json` outside Git. Regenerate the template and repeat review if any private input changes. Two different human reviewers independently fill every control-rule and mutation-target label with a verdict, evidence location, and reason before consulting agent findings. For each mutation, they also judge whether only the intended change occurred and assign its class. The adjudication section records the final labels, resolves disagreements with evidence, and explicitly approves the set. The final labels must mark every scored control rule compliant and every target mutation noncompliant with a verified single change; otherwise the case set cannot support the claimed recall and false-positive rates.

Run `python bench/compliance-mutations/finalize_labels.py /absolute/private/cases.json /absolute/private/human-labels.json` to recompute the benchmark and write a private `human-reviewed-scores.json` only after the label gate passes. Each control must also have either an agreed two-draft comparison or a source-backed adjudication record matching its scored profile and source hashes; the final result pins the comparison hash and, where applicable, the adjudication hash. This profile check has no cache TTL, so an older frozen benchmark remains reproducible, but it does not prove that the instructions are still current. The result contains reviewer IDs and input hashes, not the private labels or manuscripts. The validator checks coverage, consistency, and approval; it cannot establish the reviewers' identities, independence, or the correctness of their judgments. Keep the signed worksheet and source evidence privately for audit.
